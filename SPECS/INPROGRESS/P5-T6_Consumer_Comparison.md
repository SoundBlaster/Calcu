## What the experiment proves

The existing SDK package is consumable outside its own test imports for the
bounded offline value layer:

- `JsonDocument`, `CanonicalObjectHash` and `SurfaceSnapshot`;
- `OfflineSchemaResources` and `OfflineProposalManifest`;
- `OfflineSemanticGrantRequest` and `OfflineSelectedGrant`;
- schema instance validation and derived exposure projection.

The consumer uses its own `greeting.propose` IDs, schemas, data class, manifest,
semantic request and selected-Grant representation. Positive checks succeed and
a malformed manifest fails before any application behavior. Tests install the
packed SDK tarball in a fresh temporary directory, so they do not import SDK
`src/`, tests, or workspace links.

This demonstrates **representation-level code reuse**, not runtime reuse. The
fixture identity and Grant are intentionally synthetic: their validator success
does not make them authentic or authorized.

## Cost observed in the small consumer

| Consumer artifact | Lines | Interpretation |
| --- | ---: | --- |
| Native `greet()` behavior | 10 | Ordinary application behavior; no ASP dependency. |
| Manifest, schema resources, synthetic request/Grant construction and SDK preparation | 298 | Mostly application declarations and explicit representation wiring. SDK validates these values but does not generate them from a typed operation model. |
| Consumer tests | 33 | Three smoke/negative cases; not a conformance suite. |
| Pack/install/run harness | 59 | SDK-repository test infrastructure, not per-application integration code. |

The resulting application-first shape is clear, but the current SDK does not
yet deliver the concise action-registration or host-composition ergonomics in
the design sketches. In this consumer, describing the complete offline
representation dominates the ten-line native app. This is one fixture, not a
general effort estimate.

## Developer setup versus SDK engineering cost

- **Calcu setup:** ordinary `npm ci` consumes the repository-pinned local tarball;
  uncached transitive dependencies still require registry access.
- **Hello setup:** run `npm run test:hello-consumer` in the SDK repository. Its
  59-line harness builds/packs the SDK, installs the tarball in a disposable
  consumer directory with install scripts disabled, and asserts the app output.
- **Per-consumer ASP declarations:** Hello's 298-line representation module
  plus its schemas/IDs/policy are application-owned; they are not setup boilerplate
  generated by the SDK.
- **One-time SDK implementation cost:** not measured by this spike. No SDK
  runtime API was implemented; the 59-line harness is validation infrastructure,
  not the cost of a reusable authoring/runtime feature.

## Reuse classification after the spike

| Concern | Evidence-based disposition |
| --- | --- |
| Strict JSON, selected schemas, integrity/surface hashing, bounded manifest/request/Grant representation and exposure projection | **Reusable SDK abstraction, demonstrated.** Both consumers use the package root; the merged package comparison confirms identical exported runtime payload. These validators establish representation properties, not authorization. |
| Application action/schema/data-class declarations and handler mapping | **Concrete application configuration.** The IDs, schemas, classifications, disclosure choices, and handler wiring describe each app. No safe typed authoring model or generator is demonstrated. |
| Identity evidence verification and current lifecycle status | **Concrete trust integration; abstraction unproven.** The issuer, trust roots, verification method and status source are deployment inputs. Hello's fixture is inert and verifies none of them. |
| User authentication, consent and issuer policy | **Application policy.** These are decisions based on the app's principal, UX and policy; the Hello consumer issues no Grant. |
| Grant/session authority state, revocation, quotas and concurrency/fencing | **Concrete Calcu runtime; shared SDK extraction unproven.** Hello has no stateful runtime. Atomicity, restart recovery, race/fencing and revocation behavior need an explicit reusable contract and independent implementations. |
| Runtime/App Receipt creation and verification | **Concrete Calcu server behavior; portability unproven.** Hello has no receipt producer or verifier. Calcu's receipts are unsigned/transient and must not be presented as portable authenticated evidence. |
| HTTP/TLS server/client, request limits and cancellation | **Deployment adapter in Calcu; general abstraction unproven.** Hello uses no network. A second live host must establish transport, cancellation and failure semantics before extraction. |
| Executor and mediator | **Candidate protocol/runtime concepts, not yet proven reusable SDK components.** Calcu has concrete admission and response checks; Hello exercises representation validation only. Keep enforcement in trusted application/runtime boundaries until a second live implementation and negative tests qualify a shared API. |
| Codex CLI adapter, task host/UI, disclosure copy and calculator engine | **Concrete Calcu/provider/product integration.** They depend on Codex CLI, Calcu's four-operation domain and this local deployment; Hello provides no evidence for generalizing them into the SDK. |

## Recommendation

Keep the current offline value validators in the SDK. Do not extract Calcu's
live issuer, identity verifier, session store, executor, receipts or TLS stack
yet. The smallest justified next investigation is an offline authoring layer
that reduces repeated declaration/wiring while preserving closed schemas, exact
wire field names, explicit exposure and handler allow-lists. It may derive
declarations and schemas, but must not imply authentication, Grant issuance or
authority enforcement. Qualify it against both consumers and negative tests
before adding public APIs.

The official ASP adoption backlog still owns ADP-09 status and sequencing. This
local experiment is evidence toward that review; it does not mark ADP-09
complete or unblock it.
